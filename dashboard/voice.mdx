## Overview

Voice input lets an end user of your agent tap a microphone, speak, and get a finished, mode-shaped message — not a raw transcript. The pipeline runs on Astralform, with the providers you choose:

```
recording ──▶ speech-to-text channels ──▶ transcript ──▶ polish model ──▶ message
                (Groq, OpenAI, your endpoint —           (any connected LLM)
                 in order, until one answers)
```

The **Voice** section of an agent picks both halves. Keys stay in [LLM Providers](/dashboard/llm-providers); voice settings only reference them, and the feature cannot be turned on until both halves have a connected key. Clients never learn which vendor or model you chose — they only learn that voice input is available.

## Configuration

1. Connect a speech-to-text provider (Groq or OpenAI, or a custom OpenAI-compatible endpoint) and a polish LLM provider in **LLM Providers**.
2. Go to **Agents**, open the agent, and choose **Voice** in the Build group.
3. **Speech-to-text** — add a channel and pick its provider and model. Groq's `whisper-large-v3-turbo` is the fast default; a custom endpoint takes a model name or **Discover models**. Add a fallback channel if you have a second key — see [Speech-to-text channels](#speech-to-text-channels).
4. **Polish** — pick the provider and model that rewrite the transcript. Leave **Let the model think first** off unless you want a reasoning model's full pass; it adds 40–70 seconds before the first word.
5. Press **Test** on each speech-to-text channel and on the polish card. A channel is probed with a quarter second of silence; polish with a one-token completion.
6. Set the **Defaults**, adjust **Style prompts** and add **Vocabulary** as needed, then **Save**.
7. Turn on **Enable voice input**. The switch is refused until at least one speech-to-text channel and the polish provider are connected.

## Speech-to-text channels

Speech-to-text is an ordered list of up to five channels (provider + model), each backed by a key in **LLM Providers**. Each recording is offered to the channels in order until one returns a transcript. What a channel's failure means is an explicit rule, and a failure nobody has classified **advances** to the next channel rather than ending the request:

- **429** — the channel goes on cooldown for the time its `Retry-After` header asks (60 seconds when it says nothing, an hour at most) and the next channel takes the recording. The cooldown is shared by every backend worker.
- **The provider refuses the key** (401, 402, 403 — a revoked or wrong-team key, a region restriction, quota billed as 402/403 rather than 429) — the next channel takes the recording, and because a dead key does not fix itself the channel is parked for ten minutes so the following recordings go straight to the fallbacks. When every channel called refuses its key, the request fails as **409 `voice_not_ready`**: the keys, not the providers, are the problem. This is different from a key that is **absent from LLM Providers**: that channel is skipped before it is ever called.
- **Anything else that is not about the audio** — a 5xx, a timeout, a mis-pathed custom endpoint answering 404, a vault lookup that fails at call time on a channel that looked ready — is skipped for that recording only.
- **The provider refuses the audio itself** (400, 413, 415, 422: empty or unreadable audio, an unsupported container, a rejected language, or a 413 from a provider whose real limit is below the one documented for it) ends the request at once. Retrying would bill every key for one bad upload — and for empty audio or a rejected language the next channel would refuse it too. The container is the acknowledged exception: another channel might have taken it, which is what the ordering advice below is for. The documented limit is enforced before any call: a recording larger than a channel's documented limit never reaches it — that channel is skipped, whatever its position — and a recording larger than **every** channel's limit is a 400 without any provider being called. That ceiling counts every channel in the list, keyed or not: a custom endpoint with a 100 MB limit whose key you never connected still raises it, and a recording only that channel could have taken is skipped by every keyed channel and comes back as **409 `voice_not_ready`** — connect the key, or remove the channel, and the ceiling is honest again. Container support is **not** pre-checked the same way: a channel that refuses the recording's container ends the request even when a later channel would have accepted it. Putting the channel with the narrowest container support (typically a custom endpoint) last is the right mitigation, with one limit: cooling channels move to the back while the healthy ones keep their order, so the narrow channel becomes the first offered once **every** channel ahead of it is cooling or skipped — for a two-channel list, exactly a cooling primary; with a healthy hosted channel between them it never is. For as long as that holds, every recording in a container it refuses is a 400. Clients that send 16 kHz mono WAV are never affected by the hosted providers; a custom endpoint's accepted containers, WAV included, are yours to verify.
- A cooling channel is tried **last, not never**: the healthy channels are tried first, and only when none of them produced a transcript are the cooling ones offered the recording, in order. So a single-channel setup that keeps answering 429 keeps being tried — and when it answers 429 again the caller receives **502 `transcription_failed`**, not a 429; the project's own `voice.transcribe` limit is the only 429 a caller sees. The ten-minute key park follows the same rule with one difference: a rate-limited retry can succeed, a refused-key retry cannot until the key changes, so a key-parked channel is offered the recording only when **no other channel took the recording and failed** — a fallback that took it and failed on its own account (a 5xx, a timeout) is evidence the fallbacks are down and the dead key is not re-uploaded to; a fallback that only refused its *own* key, or answered 429 (per-key backpressure that parks that fallback), says nothing about the parked one, which is still offered the recording. That is enough for a single-channel key outage to answer **409** on every recording rather than going silent, and for a key you fixed to take effect even while a sibling's key is still dead.

Each row has its own **Test** and shows a badge; the cooldown badges say which of the two things parked the channel, because they call for different actions:

- **Primary** — the stored channel the route tries first as of this page load: the first channel that is ready and not cooling, or, when every ready channel is cooling, the first ready one. The badge is computed from stored order, readiness and the cooldowns shown; it cannot see a cooldown that starts after the page loaded.
- **Not ready** — the channel's key is missing from LLM Providers.
- **Rate-limited — tried last for …** — a 429 has parked the channel for the time its `Retry-After` asked. It clears itself; nothing to do. Pressing **Test** on this row still sends the silent probe: a pass does **not** lift the park (a quarter second of silence proves the key, not that a per-minute quota recovered), and a 429 from the probe is reported on the row but does **not** extend the park — only a real recording's 429 sets one.
- **Key rejected — save a new key** — the provider refused the key (401 / 402 / 403), and the channel is parked for ten minutes: offered a recording only when no other channel took the recording and failed on its own account. A key-rejected primary behind a fallback that returns 5xx yields that fallback's **502**, not a 409; behind a fallback whose *own* key is also refused (that is not a failure with the recording) the primary is still offered, and every key refused is the **409** that says fix your keys; behind a fallback that answers 429 the primary is offered too, but because the fallback was called and did not refuse its key the outcome is a **502**, not the 409. Saving a new key for that provider in LLM Providers lifts the park at once (the unnamed `custom` slot and a named `custom:<slug>` endpoint are different providers; saving one leaves the other's parks alone); so does pressing **Test** on the row once the key answers, for a key fixed at the vendor's end.

A single-channel setup can show either cooldown badge while still being tried on every recording: a rate-limited channel is offered the recording whenever no healthy channel anywhere produced a transcript, which with one channel is always; a key-rejected channel is offered it whenever no other channel took the recording and failed on its own account, which with one channel is also always.

Use the arrows to reorder; order is priority. Duplicate provider + model pairs are dropped on save. Polish has no failover: when the polish model fails, every client keeps the raw transcript.

End users never learn which channel answered — the transcription response carries no channel or vendor.

## Defaults

| Setting | Meaning | Default |
|---|---|---|
| **Style** | How the transcript is shaped: `raw` (no polish), `light`, `structured` (an AI-ready prompt), `formal` | `structured` |
| **Stop after silence** | In tap-to-talk mode, how long a pause ends the recording | 2 s |
| **Send when the result is ready** | Send the message as soon as polishing finishes | on |
| **Longest recording** | Cap per dictation, 10–300 s | 300 s |

Users can pick a different style per device; the default is what a fresh install gets.

## Style prompts

Each style is a system prompt. The built-in prompts ship in English and Chinese (the Chinese set is [OpenLess](https://github.com/Open-Less/openless)'s, reproduced under its MIT licence); pick the language under **Built-in prompt language**. Edit a prompt to override it, and keep `{{HOTWORDS}}` where the vocabulary block should be spliced in — a prompt without it gets the vocabulary appended when there is any. The `raw` style has no prompt: it never calls the polish model.

<Note>
The transcript is sent to the polish model as data, inside a `<raw_transcript>` envelope, with an injection-defence clause appended to every system prompt. A user cannot redirect the polish model by talking to it.
</Note>

## Vocabulary

Product names and terms the recognizer should spell correctly. The list is built once per recording and sent, as the biasing prompt, to whichever channel takes that recording — within the 240-character budget every Whisper-style channel shares, in the order you list them — and spliced into every polish prompt, where it has no budget. Users can add their own words per device; those are merged after yours.

## For client developers

The end-user API exposes the pipeline without any provider details:

- [`GET /v1/agent/status`](/api-reference/status/agent) lists `voice` under `capabilities` when the feature is enabled — the signal to show the microphone.
- [`GET /v1/voice/config`](/api-reference/voice/config) returns the modes, defaults and vocabulary.
- [`POST /v1/voice/transcriptions`](/api-reference/voice/transcriptions) turns one recording into text.
- [`POST /v1/voice/polish`](/api-reference/voice/polish) streams the rewrite as Server-Sent Events.

`/v1/voice/transcriptions` and `/v1/voice/polish` are rate-limited per project and can be tuned under [Rate Limits](/dashboard/rate-limits) as the `voice.transcribe` and `voice.polish` operations.
