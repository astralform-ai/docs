## Overview

Every agent can run code in an isolated Capsule sandbox, with nothing to switch on. A sandbox starts the first time a run calls a code or desktop tool: one per [environment](/dashboard/capsule/templates) per run.

## Lifecycle

1. **Start**: the first code or desktop tool call in a run creates the sandbox, in the environment that tool needs. Every later call of that kind in the same run uses the same sandbox.
2. **Work**: the agent runs shell commands, code and file operations inside it.
3. **Stop**: when the run ends, the agent lets go of the sandbox. The next run, even in the same conversation, starts a fresh one, so files left in a sandbox don't carry over — unless it's a routine that keeps them, below. The released sandbox shuts down after 300 seconds idle.

### Keeping files between routine runs

A routine can keep its code sandbox from one run to the next: its files, and any process a run leaves running. Turn on **Keep sandbox files between runs** when you create or edit the routine on the agent's **Routines** page, or set `persist_sandbox: true` on the routine through the API. It is off by default.

- **What carries over**: the code sandbox's whole filesystem, including installed packages, working files and anything the previous run left on disk. Files under `/workspace` are the exception: that directory is tied to the run's conversation rather than to the saved sandbox, so write anything you want next time somewhere else, such as your home directory, `/home/user`. A desktop sandbox still starts fresh every run.
- **What is fresh every run**: the restored sandbox runs code in a fresh interpreter, with the current environment variables, secrets and network access. Variables from the previous run's code are gone.
- **What else comes back**: a process the previous run left running in the background resumes too, still with that run's environment — so a secret you have since changed or revoked can still be live inside it. End long-running processes before the run finishes if you don't want them next time, or restart them to pick up the current values.
- **When the files are saved**: after a run completes successfully. A run that fails, or that runs no code, leaves the last saved files in place.
- **What discards them**: a second failed restore, at least 30 minutes after the first, with no successful restore in between. The next run then starts with an empty sandbox. An outage shorter than 30 minutes can't cost you the files, however often the routine runs. If the saved files are gone altogether, the run starts empty straight away.
- **Turning it off**: deletes the saved files.

## Network access and secrets

- **Network access** is set on **Capsule** → **Settings**:
  - **Off**: no external host is reachable.
  - **Full**: unrestricted internet access.
  - **Custom**: only the domains you list, with `*.` wildcards, IPv4 addresses or CIDR ranges.

  New agents start on **Custom**, allowing `pypi.org`, `files.pythonhosted.org` and `registry.npmjs.org`.
- **Environment variables and secrets** are set on **Settings** → **Environment**.

Network access is enforced in every [Autonomy](/dashboard/permissions) mode.

## Watching sandboxes

**Capsule** → **Pods** lists the agent's sandboxes with their state, snapshot, command count, last event, creation time and duration. You can filter by state and template. Open one to see its overview, a live terminal while it runs, and its command history.

For programmatic access, use the MCP tools `astralform_list_capsule_sessions` and `astralform_get_capsule_stats`.
