## Overview

Connect a GitHub account to your workspace and your agents can answer mentions on issues and pull requests: they read the thread, do the work, and open a PR back.

**You store nothing.** No API key, no private key, no personal access token. There is one GitHub App — Astralform's — and the workflow in your repository proves which repository it is with a GitHub-signed OIDC token.

<Note>
  Astralform holds no credential of yours here. Repository access is minted per run, scoped to the one repository the run is about, valid for an hour, and never written to a database.
</Note>

## How the pieces fit

Two things are true separately, and knowing which is which saves you a lot of clicking:

| | Scope | What it costs |
|---|---|---|
| **Connecting an account** | your whole workspace | the install trip, **once per GitHub account** |
| **Turning an agent on** | one agent | **one click** — no trip to GitHub |
| **Routing a repository** | one repository | the `agent:` line in its workflow file |

Your agents are addressed **by name from the workflow file**, so one connected account serves all of them. Point `agent: reviewer` at one repository and `agent: trader` at another and both work off the same installation.

## Setup

### 1. Connect a GitHub account

Open **Connectors** on any agent, add **GitHub**, then click **Install on GitHub**. Choose the account or organization whose repositories your agents should work in, and GitHub brings you straight back.

GitHub asks for two things — installing the app, and authorizing Astralform to confirm you administer that installation. Both happen in the same trip.

This is a **workspace** action. You do it once per GitHub account, not once per agent.

### 2. Turn on the agents that should answer

The agent you installed from is turned on automatically. For every other agent, open its **Connectors** page, add **GitHub**, and the card will already say your workspace is connected — click **Use GitHub for this agent** and you are done. No second install, no second authorization.

<Note>
  Each agent is opted in individually on purpose. Without that step, every agent in your workspace would answer the moment somebody wrote its name into a workflow file — including one you never meant to expose.
</Note>

You can connect **more than one** GitHub account to a workspace (an organization and a personal account, say). Every GitHub-enabled agent answers in all of them.

### 3. Add the workflow

Commit this to each repository the agent should answer in, as `.github/workflows/astralform.yml`. The connector page generates it with your agent's name already filled in.

```yaml .github/workflows/astralform.yml
name: Astralform

on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
  issues:
    types: [opened]
  pull_request:
    types: [opened]

jobs:
  astralform:
    if: >-
      github.event.sender.type != 'Bot' &&
      contains(github.event.comment.body || github.event.issue.body ||
               github.event.pull_request.body, '@astralform-agent')
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: astralform-ai/astralform-action@v1
        with:
          agent: your-agent-name
```

<Warning>
  `permissions: id-token: write` is **required**, not optional — it is what mints the token proving which repository is calling. Without it the action fails immediately and says so. This is the most common setup mistake.
</Warning>

The `if:` condition is yours to keep: without it, every issue, PR and comment starts a billable run rather than only the ones that mention the agent.

## The action

[`astralform-ai/astralform-action`](https://github.com/astralform-ai/astralform-action) is public and MIT-licensed. It mints the OIDC token, dispatches to Astralform, and reports back whatever Astralform said — so a refusal tells you *why* rather than failing as an opaque non-zero exit.

| Input | Required | Default | Description |
|-------|----------|---------|-------------|
| `agent` | yes | — | The agent's **name** as shown in the dashboard. |
| `instruction` | no | the triggering body | What to ask. Defaults to the comment, issue or PR body that fired the event. |
| `issue-number` | no | the triggering number | The issue or PR the run is about. |
| `api-url` | no | `https://api.astralform.ai` | Only for a self-hosted deployment. |
| `audience` | no | `https://api.astralform.ai` | OIDC audience. Change only alongside `api-url`. |

### Pinning

`@v1` is a moving major tag — it follows every backwards-compatible release. Because the action runs on your runner with `id-token: write`, you may prefer something stricter:

| Pin | What you get |
|-----|--------------|
| `@v1` | Fixes and features arrive automatically. The tag moves. |
| `@v1.0.1` | Immutable. A repository ruleset blocks deletion, update and force-push on every `v*.*.*` tag. |
| `@<full-sha>` | Immutable and independent of our tagging. Dependabot and Renovate keep SHA pins current. |

## Who can start a run

The OIDC token proves which **repository** is calling. It says nothing about **who** commented — so Astralform checks that separately, and only an `OWNER`, `MEMBER` or `COLLABORATOR` of the repository may start a run.

A stranger commenting `@astralform-agent` on your public repository is refused server-side, whatever the workflow does.

Runs are also rate limited: **10 per repository per minute** and **60 per account per minute**. Authorization answers *whether* someone may start a run, not *how many*.

## What the agent can touch

The token minted for a run carries only what the work needs:

| Permission | Level |
|------------|-------|
| `contents` | write |
| `issues` | write |
| `pull_requests` | write |
| `metadata` | read |

`workflows` is deliberately absent. A mention-driven run cannot rewrite the CI that runs on every future push.

## Repository access

The connector page lists the repositories your installation covers and flags which ones have the workflow committed — granting access and adding the workflow are two separate steps, and the second is the one people forget.

| Label | Meaning |
|-------|---------|
| **Workflow file found** | `astralform.yml` or `astralform.yaml` exists in `.github/workflows`. |
| **No workflow file** | Neither exists there. Mentions still work if you put the job in another workflow file. |
| **Not checked** | GitHub did not answer for that repository, so its status is unknown — not a claim that anything is missing. |

**Changing which repositories are covered happens on GitHub**, via the **Change on GitHub** link. GitHub's API for adding and removing repositories on an installation accepts only a classic personal access token with full `repo` scope, and asking you for one would mean Astralform holding read/write on every repository you own in order to manage a list.

## Turning it off

Two different scopes, matching the two in [How the pieces fit](#how-the-pieces-fit):

| Action | Where | Effect |
|--------|-------|--------|
| **Uninstall** the connector | the connector page's menu | This agent stops answering. Your workspace stays connected, other agents carry on, and turning this one back on is a single click. |
| **Disconnect** an account | next to the account on the card | **Every** GitHub-enabled agent in the workspace stops answering in that account. The confirmation says how many that is before you commit. |

Neither removes the app from your GitHub account — that is yours to do in your GitHub settings, and the card links you there.

Disconnecting an account does not remove the connector from any agent, so reconnecting later does not mean re-adding GitHub to each agent by hand.

## Troubleshooting

### The card says "Setup Required" after installing

The install and the authorization are separate legs, and reconfiguring an app you have already installed has no authorization leg at all. Open the connector and click **Install on GitHub** again — it will ask only for the missing half.

### The workflow fails immediately

Check `permissions: id-token: write` is on the job. The action names this explicitly when it is missing.

### Mentions do nothing

1. Confirm the workflow is committed on the repository's **default branch**.
2. Confirm the commenter is an `OWNER`, `MEMBER` or `COLLABORATOR`.
3. Confirm the agent named in `agent:` has GitHub **turned on** — open its Connectors page and check the card does not say *"Your workspace is already connected"* with an un-clicked button.
4. Confirm `agent:` matches the agent's name in the dashboard exactly — names resolve only inside the GitHub account that owns the repository.

### A second agent asks me to install again

It should not, and no longer does. If a card offers the full install flow while another agent in the same workspace is already connected, the account it was connected to has been disconnected or the app was removed on GitHub — reconnect it once and every agent picks it up.

### "That GitHub account is already connected to another workspace"

One GitHub account belongs to one Astralform workspace. Disconnect it in the other workspace first.
