title: "Local Docker Stack"
description: "Run the full development stack, or use isolated PostgreSQL, Redis and S3 storage for Harness acceptance without the production database tunnel."
---

The local development stack runs every Astralform service in Docker, wired
together by a single `docker-compose.dev.yml`. One command brings the whole
platform up; source changes hot-reload without a rebuild.

<Warning>
The full `docker-compose.dev.yml` stack opens an SSH tunnel to the **production database**. Local HTTP ports do not mean local data. Do not use this stack for migration or integration acceptance; use [isolated Harness acceptance](#isolated-harness-acceptance) below.
</Warning>

## What you get

| Service | Host port | Role |
| --- | --- | --- |
| `dashboard` | `http://localhost:5173` | React + Vite dashboard SPA |
| `chat` | `http://localhost:5174` | AstralChat (the canonical end-user chat surface) |
| `auth-spa` | `http://localhost:5175` | OAuth consent + login UI |
| `api-gateway` | `http://localhost:8000` | nginx — mirrors prod Traefik path routing |
| `auth-backend` | `http://localhost:8090` | FastAPI — OAuth 2.1 Authorization Server + identity |
| `backend` | (internal) | FastAPI + native agent loop — `/v1/*` routed by the gateway |
| `redis` | `127.0.0.1:6379` | SSE event distribution (TCP — not an HTTP endpoint) |

The gateway at `:8000` mirrors what `api.astralform.ai` does in production:
OAuth and admin prefixes route to `auth-backend`, everything else to the
main `backend`. The split is invisible to clients — calling
`localhost:8000/oauth/authorize` and `localhost:8000/v1/jobs` works the same
way `api.astralform.ai` does in prod.

## Prerequisites

- **Docker** — [OrbStack](https://orbstack.dev/) recommended on macOS, Docker
  Desktop works too
- **Three sibling repos** checked out next to each other:
  ```text
  ~/yourcode/
  ├── Astralform/         ← this repo (backend + dashboard + compose)
  ├── astralform-auth/    ← auth backend + auth SPA
  └── astralform-chat/    ← chat SPA
  ```
- A populated `Astralform/.env` (copy from `.env.example`)

## Bring it up

```bash
cd Astralform

# First-time build of the backend image (only after Dockerfile changes)
docker compose -f docker-compose.dev.yml build

# Daily — start everything in the background
docker compose -f docker-compose.dev.yml up -d
```

Wait ~10 seconds for the backend's healthcheck to flip green, then visit
[http://localhost:5174](http://localhost:5174) to use AstralChat or
[http://localhost:5173](http://localhost:5173) for the dashboard.

## Tail logs

```bash
# Everything, interleaved
docker compose -f docker-compose.dev.yml logs -f

# One service
docker compose -f docker-compose.dev.yml logs -f backend
docker compose -f docker-compose.dev.yml logs -f chat
```

Backend logs also rotate daily to `backend/logs/backend_YYYY-MM-DD.log` on
the host (bind-mounted), so you can `grep` historical lines without
spelunking through `docker logs`.

## Hot reload

Source changes are picked up automatically — no restart needed:

- **Python** changes → uvicorn's `--reload` flag re-imports modules
- **TypeScript / React** changes → Vite HMR pushes updates over WebSocket

Restart a single service only when you've changed environment variables or
dependencies:

```bash
docker compose -f docker-compose.dev.yml restart backend
```

## Run tests

Run the repository's offline backend gate from the repository root:

```bash
bash scripts/ci-local.sh backend
```

The gate selects `not integration` and supplies safe CI settings. Do not run an unfiltered `pytest tests/` against the full dev stack or a production `.env`: existing integration tests may reach production. Real datastore acceptance uses the separate stack below.

## Isolated Harness acceptance

`docker-compose.harness-smoke.yml` starts only PostgreSQL 17, Redis and MinIO. It does not start the SSH tunnel, auth services, dashboard, cloud Actor or Harness. All published ports are ephemeral and loopback-only.

### Prepare the worktree

- Use a dedicated worktree and a **local** Docker context. Remote Docker endpoints are refused.
- Ensure this worktree contains no root or `backend/.env`. Preserve any existing file under an ignored backup name; do not delete or change the shared checkout's configuration. Clearing process environment alone does not disable the backend's dotenv loading.
- Install the backend environment with `uv sync --locked --extra dev` from `backend/`.
- Obtain the approved MinIO image from the operator's trusted image store. The stack checks the exact digest pinned in the compose file; it does not substitute a floating image if that pin is absent.

### Obtain the complete schema baseline

An operator supplies `.harness-smoke/baseline/public.sql` and `manifest.json`. They are local inputs, not committed fixtures:

- Export PostgreSQL 17 **schema only**, with `pg_dump --schema-only --no-owner --no-acl --schema=public`, through a read-only source operation. Never export customer rows or a full production dump.
- The manifest has `format_version: 1`, `schema_sha256`, the complete `migrations` list of actual `public.schema_migrations.version` filename stems, and a `source` object with `database`, `server_version` and `exported_at`.
- Record the ledger around the export and refuse a changed source ledger. The SHA256 covers the original SQL bytes. Do not infer applied migrations from a numeric prefix or construct a small substitute schema.

The importer verifies provenance, this checkout's exact compose ownership and a fresh empty target before writing. It runs the existing PostgreSQL bootstrap plus the complete schema transactionally, then records exactly the manifest ledger. Unknown or incomplete history is refused; newer local files remain unapplied for the forward migration runner. A failed or repeated import is not a request to wipe the database: use this project's `down`, then `up` and import again.

### Run the datastore proof

From the repository root, choose a project name unique to this worktree:

```bash
export HARNESS_SMOKE_PROJECT=harness-smoke-my-branch
bash scripts/harness-smoke.sh up
bash scripts/harness-smoke.sh import-schema
bash scripts/harness-smoke.sh check --json
```

`up` discovers actual published ports; it never assumes the full dev stack's ports. `check` verifies the real PostgreSQL ledger/tables, performs unique-key Redis and object-storage round trips, and deletes only its probe key/object. A failure returns nonzero. The redacted report is `.harness-smoke/check-report.json`; local credentials and state also remain ignored under `.harness-smoke/`.

### Start the real backend

From `backend/`, use the same project name and a free API port. The clean environment prevents ambient production tokens from being inherited; the worktree must still have no dotenv file:

```bash
env -i PATH="$PATH" HOME="$HOME" \
  HARNESS_SMOKE_PROJECT=harness-smoke-my-branch \
  bash --noprofile --norc -c '
    set -euo pipefail
    test ! -e ../.env && test ! -e .env
    eval "$(bash ../scripts/harness-smoke.sh env)"
    export API_BASE_URL=http://127.0.0.1:18090
    exec uv run uvicorn src.main:app --host 127.0.0.1 --port 18090
  '
```

In another terminal, `curl --fail http://127.0.0.1:18090/v1/health` must return HTTP 200. This is backend/datastore startup proof, not proof of a cloud Actor or model invocation. `env` intentionally contains local credentials: capture it in the launching shell, never paste it into issue reports.

Stop the backend before removing its datastores, then run from the repository root:

```bash
HARNESS_SMOKE_PROJECT=harness-smoke-my-branch bash scripts/harness-smoke.sh down
```

Cleanup requires this checkout's owned containers or recorded project state. It refuses foreign checkout containers and unowned orphan volumes; no global prune or unrelated dev-stack shutdown is performed.

### Harness catalog and team enablement

Run this section **before the `down` step above** — the isolated database must
still be up. Delegation runs against immutable releases, not mutable catalog
rows. The operator flow (all commands from `backend/` with an explicit
`DATABASE_URL`):

```bash
# 1. Publish a digest-bound release — the real image gate must pass first.
#    The release manifest (image digest, adapter/profile, capabilities,
#    configuration schema, provenance) is a separate contract from the schema
#    baseline manifest above.
uv run python scripts/publish_harness_release.py \
  --slug deepseek-harness --version 2026.11.06 --manifest /path/to/release-manifest.json

# 2. Reconcile legacy visibility into explicit team enablement (create-only,
#    never broadens: legacy agent allowlists stay enforced).
uv run python scripts/reconcile_harness_admission.py
```

Team admins manage visibility through the catalog API: `GET /v1/harness-releases`
(operator), `GET /v1/teams/{team}/harness-catalog` (member), and
`PUT /v1/teams/{team}/harness-releases/{release}/enablement` (team admin). The
enablement body cannot carry an image or capabilities — those come only from the
release manifest — and every change is audit-logged.

Admission is a dual gate: a delegation needs a published release, an enabled
team-release row, and (for harnesses with a legacy allowlist) the requesting
agent in that allowlist. An empty allowlist remains *nobody* for external
harnesses; team enablement alone never grants one. `seed_harness.py --image`
refuses to move a published release's image (publish a new release instead).

## Stop the full dev stack

```bash
docker compose -f docker-compose.dev.yml down
```

Named volumes (`dashboard_node_modules`, `chat_node_modules`, etc.) survive
between runs so `npm install` doesn't fire on every `up`.

## Common gotchas

These are failure modes specific to running in containers — they don't show
up when you run a single service host-side.

### `localhost` from inside a container is the container itself

A Vite proxy that targets `http://localhost:8000` will hit the SPA's own
port 8000 (which isn't bound to anything), not the host's gateway. The
compose file injects Docker DNS hostnames for container-to-container calls:

```yaml
environment:
  BACKEND_URL: http://api-gateway:80          # chat → gateway (container port)
  AUTH_BACKEND_URL: http://auth-backend:8000  # auth-spa → auth-backend (container port; host sees 8090)
  AUTH_BASE_URL: http://auth-backend:8000     # backend's JWKS fetch (container port; host sees 8090)
```

If you see a SPA silently failing on its initial `/oauth/*` or `/v1/*`
calls inside the stack, this is the first thing to check.

### OrbStack's IPv6 port-publish resets streams

Connections to `[::1]:PORT` drop after the handshake on some OrbStack
versions. The compose file binds publishes to `127.0.0.1:PORT:PORT`
explicitly so browsers fall back to IPv4 cleanly. If you remove the
`127.0.0.1:` prefix, curl needs `-4` to reach the service.

## Host-side fallback

The standalone scripts at `scripts/dev-backend.sh` and
`scripts/dev-frontend.sh` are still around for the case where you want to
iterate on a single service against the host's `.venv` / `node_modules`
— for example, to attach a debugger or test a tricky dependency in
isolation.

If you run a script while the docker stack is up, you'll get a port
conflict. Stop the matching docker service first:

```bash
docker compose -f docker-compose.dev.yml stop backend
cd backend && ../scripts/dev-backend.sh
```
