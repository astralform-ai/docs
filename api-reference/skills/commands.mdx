---
title: "List Slash Commands"
api: "GET /v1/skills/commands"
description: "Get the slash commands a chat surface can offer: system commands plus the agent's enabled skills."
---

Slash commands are the agent's skills. Every enabled skill whose command is on (the default) is
available as `/<skill-name>`, and a
small set of system commands sits in front of them. This endpoint returns the list a composer's
`/` menu should offer — the same catalog-derived list the Telegram bot uses for `/help` — so
clients never hardcode commands and a newly enabled skill appears with no client change.

Sending a command is just sending a message: post `/<name> <args>` as the `message` of a
job ([`POST /v1/jobs`](/api-reference/chat/stream)). The backend resolves it; nothing about the request changes.

## Authentication

<ParamField header="Authorization" type="string" required>
  Your project API key as a bearer token (`Bearer sk_xxxxxxxxxxxx`), or an end-user token.
</ParamField>

## Query parameters

<ParamField query="surface" type="string" default="web">
  Who will execute the commands. A surface is only told about the commands it can run:

  - `web` — clients of [`POST /v1/jobs`](/api-reference/chat/stream) (the chat SPA, the iOS app, SDK apps). Lists `/goal`,
    `/plan` and the enabled skills whose command is on.
  - `telegram` — the Telegram bot. Lists `/new`, `/goal`, `/tasks`, `/help` and the same
    skills, with Telegram-valid names (hyphens become underscores).
  - `all` — every command, unfiltered, for a discovery UI. Every row carries `surfaces`
    whichever value you pass.
</ParamField>

## Response

A JSON array of command objects: system commands first, then enabled skills.

<ResponseField name="command" type="object">
  One row of the array.
  <Expandable title="Command object">
    <ResponseField name="name" type="string">
      The command name, without the leading slash
    </ResponseField>
    <ResponseField name="display_name" type="string">
      Human-readable name
    </ResponseField>
    <ResponseField name="description" type="string">
      One line for the menu row
    </ResponseField>
    <ResponseField name="args_hint" type="string">
      Argument hint to show after the name: a system command's own (`<objective>`), a skill's
      `metadata.command-hint` if set, otherwise `[args]`; empty when there is no argument
    </ResponseField>
    <ResponseField name="surfaces" type="string[]">
      Surfaces that can execute this command (`web`, `telegram`)
    </ResponseField>
  </Expandable>
</ResponseField>

## System commands

| Command | Surfaces | What it does |
|---------|----------|--------------|
| `/goal <objective>` | web, telegram | Starts a durable autonomous goal — the same request the composer's Goal mode sends. |
| `/plan <request>` | web | Runs a read-only planning turn — the same as Plan mode. |
| `/new` | telegram | Starts a fresh conversation. |
| `/tasks` | telegram | Lists the goals started in this chat. |
| `/help` | telegram | Lists the commands, including enabled skills. |

`/new`, `/tasks` and `/help` are chat actions the job API has no equivalent for — a web client
has its own New chat button, and its `/` menu is the help — so they are not advertised to the
`web` surface.

## Usage notes

- A skill command seeds the turn with the skill's full instructions, then runs the request
  normally. The text the user typed stays on their message; only the model sees the seed.
- A skill whose name collides with a system command is not exposed as a command.
- A skill whose command is turned off — `metadata.command: "false"` in its SKILL.md, or
  **Slash command: Off** on its dashboard page — is not listed and `/<name>` is sent as
  ordinary text. See [Skills → Turning a command off](/dashboard/skills#turning-a-command-off).
- `/goal` and `/plan` without an argument return `400` with the usage hint.
- Anything that is not a recognized command is sent to the agent as ordinary text, so an
  unknown `/foo` behaves exactly like a plain message.
