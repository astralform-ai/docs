---
title: "Transcribe a Recording"
description: "Turn one recording into text with the agent's speech-to-text channels, tried in order."
api: "POST /v1/voice/transcriptions"
---

## Endpoint

```
POST https://api.astralform.ai/v1/voice/transcriptions
```

Accepts an API key or an end-user OAuth token with `X-Agent-ID`; both forms are shown on [Voice Config](/api-reference/voice/config).

## Request

`multipart/form-data`:

| Part | Type | Required | Description |
|------|------|----------|-------------|
| `file` | file | Yes | The recording. 16 kHz mono 16-bit WAV is the reference format and every channel accepts it. Another container works only if the **first channel that is offered the recording** accepts it: unlike the size limit, container support is not checked before the call, so a channel that refuses the container ends the request as a **400** even when a later channel would have taken it. The hosted providers take WAV, MP3, M4A, WebM/Opus and FLAC; a custom endpoint decides for itself. Put the channel with the narrowest container support last; it becomes the first offered only once every channel ahead of it is cooling or skipped (for a two-channel list, a cooling primary), and for as long as that holds every recording in a container it refuses is a 400. Sending WAV is the client-side way out. |
| `hotwords` | string | No | The user's own vocabulary, comma-separated — not the project's, which the server already holds. A word cannot itself contain a comma. |
| `language` | string | No | ISO 639-1 hint (`en`, `zh`). Omit for auto-detection. |

The server merges the project vocabulary with these words, project words first, cuts the result once at the 240-character budget, and sends that same prompt to whichever channel takes the recording.

```bash
curl -X POST https://api.astralform.ai/v1/voice/transcriptions \
  -H "Authorization: Bearer sk_xxxxxxxxxxxx" \
  -F "file=@clip.wav;type=audio/wav" \
  -F "hotwords=MCP, LangGraph"
```

## Response

```json
{
  "text": "let's ship the voice feature on friday",
  "language": "en",
  "duration_ms": 4120,
  "asr_ms": 610
}
```

| Field | Type | Description |
|-------|------|-------------|
| `text` | string | The transcript as the channel that answered produced it. |
| `language` | string \| null | The language that channel detected. |
| `duration_ms` | integer \| null | Length of the recording, when the WAV header says so. |
| `asr_ms` | integer | Wall-clock time of the whole speech-to-text step, from the first channel tried to the transcript — including the seconds spent on channels that failed or timed out before one answered. A rising `asr_ms` with a healthy transcript is the sign a primary channel is going bad. |

Which channel answered is never reported: naming one by elimination would name a vendor, and an end-user token must not learn which vendor the developer configured.

## Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | — | Empty recording; larger than every configured channel's limit (25 MB for the hosted providers — checked before any call, so a channel whose limit the recording exceeds is skipped without a call); or refused by a provider as unusable audio (its 400 / 413 / 415 / 422), which ends the request because retrying would bill every key for one bad upload — for empty audio or a rejected language the next channel would refuse it too; a refused container is the exception, since a later channel might have taken it (see `file` above). The pre-flight counts configured channels, keyed or not: a recording that passes it because a keyless channel has the higher limit, but which every channel with a key is too small for, is never sent anywhere and comes back as the 409 below. |
| 409 | `voice_not_ready` | Voice input is disabled, no speech-to-text channel has a key in LLM Providers, no channel could be called at all (every keyed channel too small for the recording, see the 400 row), or every channel that was called refused its key (401 / 402 / 403). |
| 429 | — | The project's own `voice.transcribe` rate limit. A provider's 429 never reaches the caller: that channel goes on cooldown and the next configured channel takes the recording; when no channel is left, the outcome is the 502 below. |
| 502 | `transcription_failed` | Every channel that could take the recording failed to return a transcript — including a single channel answering 429 again while still cooling (a cooling channel is tried last, not never; the request does not wait the cooldown out). A channel skipped without a call (over its size limit, key-parked and not offered, no key in LLM Providers) is not counted. Details are logged server-side; the response names no vendor. |
