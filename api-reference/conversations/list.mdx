---
title: "List Conversations"
description: "Retrieve a page of conversations for the authenticated end user, newest-updated first."
api: "GET /v1/conversations"
---

## Endpoint

```
GET https://api.astralform.ai/v1/conversations
```

Conversations are returned **newest-updated first** (`updated_at` descending).

## Request

### Headers

```
X-API-Key: af_live_xxxxxxxxxxxx
```

The list is scoped to the end user your credential identifies — Astralform derives that from the key itself, so no end-user header is needed.

### Query Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `limit` | integer | 50 | Conversations per page. Maximum 100. |
| `offset` | integer | 0 | Pagination offset. Minimum 0. |

## Response

A JSON **array** of conversation objects — there is no wrapper object.

```json
[
  {
    "id": "conv_abc123",
    "title": "Q3 earnings review",
    "message_count": 5,
    "created_at": "2024-01-15T10:30:00Z",
    "updated_at": "2024-01-15T10:35:00Z"
  },
  {
    "id": "conv_def456",
    "title": "Refactor the payments worker",
    "message_count": 12,
    "created_at": "2024-01-14T09:00:00Z",
    "updated_at": "2024-01-14T09:15:00Z"
  }
]
```

### Conversation Object

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique conversation identifier |
| `title` | string | The conversation's name — see below |
| `message_count` | integer | Number of messages in the conversation |
| `created_at` | string | ISO 8601 creation timestamp |
| `updated_at` | string | ISO 8601 last-activity timestamp |

<Note>
  `title` is never null. The server names a conversation from its first turn; until then this field falls back to the first 8 characters of the conversation ID, so treat an ID-looking title as "not yet named" rather than as a real name. Users can replace it with [Rename Conversation](/api-reference/conversations/rename).
</Note>

## Example

### cURL

```bash
curl -X GET "https://api.astralform.ai/v1/conversations?limit=10" \
  -H "X-API-Key: af_live_xxxxxxxxxxxx"
```

### Swift

```swift
let conversations = try await client.listConversations(
    limit: 10,
    offset: 0
)

for conv in conversations {
    print("\(conv.id): \(conv.messageCount) messages")
}
```

## Pagination

Page with `limit` and `offset`:

```bash
# First page
GET /v1/conversations?limit=50&offset=0

# Second page
GET /v1/conversations?limit=50&offset=50
```

The response carries **no total count**. Infer whether more remain from the size of the page you got: a full page means there may be another, and a short page means you have reached the end.

```javascript
// @astralform/js >= 4.3.0
const limit = 50;
const page = await client.getConversations(limit, offset);
const mayHaveMore = page.length === limit;
```

A total that happens to be an exact multiple of the page size therefore costs one extra empty request before you learn you are done — cheaper than adding a count query to every list call.

<Warning>
  Offset paging is only stable while the rows before your offset are. A conversation bumped to the top by a new message — from a routine, or another device — shifts everything down by one, so a page fetched afterwards can skip a row. Re-fetching from offset 0 recovers it; nothing is lost server-side.
</Warning>

## Caching

The list is per-user and changes whenever a conversation is created, renamed, or deleted, so it is **validated rather than cached**:

```
Cache-Control: private, no-cache
ETag: "a37f16fa0c7d3fda…"
```

`no-cache` does not mean "do not store" — it means the response may be stored but must be revalidated with the server before every reuse. Send the `ETag` back as `If-None-Match` and you get a bodiless **304 Not Modified** when nothing has changed:

```bash
curl -X GET "https://api.astralform.ai/v1/conversations?limit=20" \
  -H "X-API-Key: af_live_xxxxxxxxxxxx" \
  -H 'If-None-Match: "a37f16fa0c7d3fda…"'
```

The validator is derived from the response body, not from timestamps — [renaming a conversation](/api-reference/conversations/rename) deliberately leaves `updated_at` untouched, so a timestamp-based validator would report "unchanged" for a title the user just edited.

<Note>
  Browsers revalidate on their own. Application code needs the header explicitly: `ETag` is exposed via `Access-Control-Expose-Headers` and `If-None-Match` is allowed cross-origin, so a browser-based client can read and send it.
</Note>
